# 系统架构

## 分层架构

```
用户层     Web 前端 (Vue3 + Element Plus)
         ┌──────────────────────────────┐
         │  智能问答 / 知识库文档 / 管理后台 │
         └──────────────┬───────────────┘
                        │ HTTP (JWT)
API 层    ┌─────────────▼────────────────┐
         │   FastAPI (FastAPI + Pydantic) │
         │   认证 → RBAC → 多租户数据过滤  │
         └──────────────┬───────────────┘
                        │
检索/问答层 ┌─────────────▼────────────────┐
          │ 查询改写(rule/LLM) → 混合检索 → Rerank │
          │ → 上下文组装(防注入) → LLM → 引文标注   │
          └──────────────┬───────────────┘
                        │
文档层     ┌─────────────▼────────────────┐
          │ 上传 → 分页解析(扫描件OCR) → 清洗  │
          │ → 按类型分块(句子对齐+页码) → 向量化 │
          └──────────────┬───────────────┘
                        │
基建层    ┌──────────────▼────────────────┐
         │ PostgreSQL(元数据) Redis(队列)   │
         │ Milvus(向量)  Prometheus(指标)  │
         └────────────────────────────────┘
```

## 请求链路

**问答**：`前端 → POST /api/v1/chat` → 鉴权(JWT) → 检索（混合检索 + 权限过滤）→ LLM 生成 → 返回答案 + 引文

**上传文档**：`前端 → POST /api/v1/documents/upload` → 鉴权 + 去重 → 落盘 + 建记录(pending) → 投递 Celery 任务 → 立即返回 → worker 异步解析入库

**可观测埋点**：每次问答落一条 `query_traces`（问题/改写/缓存命中/检索数/延迟/答案预览）写入 PostgreSQL；同时累加 Prometheus 指标（`rag_questions_total` / `rag_llm_calls_total` / `rag_llm_errors_total` / `rag_no_answer_total` / 延迟直方图），由 `:8000/metrics` 暴露、Prometheus `:9090` 抓取。

**反馈闭环**：回答点赞/点踩 → `POST /api/v1/chat/messages/{id}/feedback` → 管理端汇总 → `scripts/export_badcases.py` 导出坏例供人工审核并入评测集。

## 多租户权限设计（核心亮点）

- 每个用户有 `department`（部门），每个文档有 `department`（归属部门）
- 检索时构造 Milvus 元数据过滤条件 `department == "<用户部门>"`，从向量层就隔离数据
- 后端再做二次校验：越权访问文档时返回 403（双层防护）
- 管理员可跨部门；经理可管理本部门

## 技术决策

| 决策 | 理由 |
|---|---|
| 文档处理用 Celery 异步队列 | 解析/OCR/向量化耗时，不能阻塞上传接口 |
| Milvus 而非简单向量库 | 原生支持标量字段过滤，权限落在检索层 |
| 回答必带引文 | 降低幻觉 + 企业可信度要求 |
| 检索管线自研 | 面试能讲清原理，而非调包 |
| docker-compose 而非 K8s | 该体量 K8s 是过度设计 |
